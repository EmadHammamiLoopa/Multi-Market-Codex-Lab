## Decision grid and causal option-flow clock

Decisions are evaluated on the existing one-minute target-market decision grid.

Option trades use Tardis `local_timestamp` as the causal availability clock.

For a decision at time `t`, only option trades satisfying:

`local_timestamp < t`

may be used.

A trade with `local_timestamp == t` is not available at `t`.

The maximum option-flow lookback is 30 minutes.

The four frozen trailing windows are:

- 1 minute: `[t-1m, t)`;
- 5 minutes: `[t-5m, t)`;
- 15 minutes: `[t-15m, t)`;
- 30 minutes: `[t-30m, t)`.

No previous-day option trades are used. EXP010 begins its audited readiness grid at 00:30 UTC so every 30-minute option window used within the intended support region is same-day causal history.

No forward fill, interpolation, synthetic trade, quote-derived pseudo-trade, or surface-derived value is allowed.

## Frozen eligible BTC option universe

Include only vanilla BTC options matching either:

- standard/inverse: `BTC-<expiry>-<strike>-C/P`;
- USDC-linear: `BTC_USDC-<expiry>-<strike>-C/P`.

No ETH option, combo instrument, future, perpetual, spot instrument, or malformed/unrecognized symbol is allowed.

Both standard and BTC_USDC option trades are combined into the BTC flow block.

Tardis `side` is interpreted exactly as the liquidity-taker/aggressor side reported in the frozen trades CSV.

Trade `amount` is used as the exchange-provided option amount. No option trade price is used as a predictor in EXP011.

This avoids mixing inverse option premium prices with USDC-linear premium prices.

## Frozen option-flow support rule

At a decision `t`, the complete flow block is valid only if every frozen window {1m,5m,15m,30m} contains at least one eligible BTC option trade.

Because windows are nested, this will ordinarily be determined by the 1-minute window, but the implementation must explicitly verify all four windows.

A missing complete block removes that decision from common support.

No zero-imputation is permitted for an empty window.

## Frozen flow feature family F

Exactly 24 option-flow features are allowed.

For each window `w` in {1,5,15,30} minutes, define over eligible trades in `[t-w,t)`:

- `N` = total trade count;
- `A` = sum of positive trade amounts;
- `A_buy`, `A_sell` = amounts by aggressor side;
- `A_call`, `A_put` = amounts by option type.

All denominators below must be strictly positive; otherwise the decision is not complete support.

For each window, include exactly these six features:

1. `log1p(N)` — trade-count intensity;
2. `log1p(A)` — option-amount intensity;
3. `(A_buy - A_sell) / (A_buy + A_sell)` — signed aggressor amount imbalance;
4. `abs((A_buy - A_sell) / (A_buy + A_sell))` — aggressor pressure magnitude;
5. `(A_call - A_put) / (A_call + A_put)` — signed call/put amount imbalance;
6. `abs((A_call - A_put) / (A_call + A_put))` — call/put composition magnitude.

Across four windows this yields exactly 24 features.

No trade-price feature, IV feature, strike bucket, delta bucket, expiry bucket, moneyness bucket, block-trade classifier, whale-size threshold, notional conversion, quote feature, options-surface feature, open-interest feature, Greeks feature, or interaction term may be added under EXP011.

No feature selection is performed after outputs are opened.

### Why absolute imbalance is frozen ex ante

The target is opportunity magnitude independent of direction. A linear logistic model using only signed flow could miss a symmetric relation in which unusually strong buying or unusually strong selling both precede large opportunities. Therefore both signed imbalance and its absolute magnitude are preregistered before scoring.
